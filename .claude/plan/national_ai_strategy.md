## 1. 设计目标与边界

AI 不应是“有钱就购买、有人就出击、见敌就招募”的规则集合，而应是一个国家级指挥系统：每笔支出对应任务，每名英雄有持续命令，每次进攻有后勤预算，每座危险城池有防御或撤离方案。

优先级为：合法行动与资源一致性 → 排除可避免的危险溢员 → 国家存续 → 核心战力保全 → 扩张与统一 → 经济效率。保命不是永久龟缩的借口；当安全、可供养的扩张方案存在时，必须产生实际行动。

“像真人”在本方案中的含义是：会比较完整方案、承认打不过、保存实力、支援老家、选择交战地点、利用规则，而不是增加作弊资金或读取未来。不能承诺在随机战斗和动态对手下求得数学上的全局最优；目标是在受限计算量下选取合法候选中风险与长期收益最好的方案。

本阶段不引入神经网络、联网大模型、无限深度搜索、全游戏 ECS 重构，也不顺便改变失城清除、守将顺序、撤退概率等玩法。改动 AI 策略与统一命令入口可以实施；改变游戏规则必须另立决策，不可藏在 AI 实现里。

AI 禁止创建或调用 `NesBattleKernel`、`BattleSimulation` 试打未来战斗，禁止随机采样、蒙特卡洛、逐帧或逐碰撞推演，也禁止以“简化模型”逐轮扣血直到胜负确定。不使用离线批量试打生成的对局胜率表来变相实现同一功能。真实已经发生的游戏战斗继续使用原有引擎；独立运行游戏的回归验证不属于 AI 决策能力，不把未来测试结果喂给当前决策。

允许的是有界的静态算术：属性修正、合法武器伤害区间、现金与兵员预算、路线耗时、守将出场资格、候选行动收益比较。静态风险估计不是事实胜率，也不能宣称未来一定获胜。

### 2.1 现有 AI 的关键缺口

初稿核对的 `_decideCountry` 发现威胁后，只对最多两城执行升级、招将、补兵，没有对守将出场资格、撤离和全国回援做联合规划。`_manageAiFieldArmies` 主要依据资金返城，不承担保卫老家的任务。现有 `_projectRaid` 虽然不调用真实内核，但会循环推算换将、伤亡与剩余兵力，不能直接作为本次“无战斗模拟”评估器保留；应被静态评估与规则检查替代。证据：`country_strategy.dart:174–199,474–555`；`country_ai.dart:112–176`。

本次补充核对发现 `campaign_weapons.dart` 已出现 `_tryAutomaticWeapons`：开场及新碰撞驱动自动释放，涉及背包首件和概率判定。此处属于并行演进中的真实玩法；新 AI 必须读取同一份释放规则描述，只决定玩家同样能控制的装载、排序与行动，不另开 AI 专用的必定释放或任意提前使用入口。

现有预算对粮草和月结前后的现金低点已有处理，应该复用、扩展，而不是推倒后退回简单的 `gold > cost`。见 `country_ai_budget.dart:33–186`。

## 3. 战时守城安全：本次最高优先级

### 3.1 定义真正的安全名额

定义 `H(c)` 为城内存活的本国驻军数，包含当前正在守城的英雄，不包含已离城的行军、扎营、排队及野战部队。

未开战时：

```text
B(c) = 当前城池等级
```

正在进行攻城时：

```text
B(c) = max(0, battle.initialCityLevel - battle.victories)
```

`B` 是从现在开始、敌人仍可能通过获胜耗尽的守城名额，包含当前这轮；不是建筑面板上刚升完的等级。换守将、城防受损、战斗结束、援军入城后都必须重算。

处于明确进攻威胁下的城池，AI 计划提交后必须满足：

```text
H(c) <= B(c)
```

并且关键英雄要么能按真实顺序在失城前出战，要么已有可验证的安全转移方案。不能满足数量条件后就宣称防御成功；还需评估属性对局优势、空城风险、后续来敌和全国损失。

这一上限优先于 `requiredGarrison` 和招募容量。战时禁止签入新的危险溢员；回援入城前必须预留安全名额。和平时期可在安全后方暂时集中整备，但要有疏散时限与危机预案，边境不长期囤积超过名额的将领。

### 3.2 “绝对不能出现”的工程契约

可控部分做硬约束：AI 不得提交会制造危险溢员的普通计划；确认威胁后不得把溢员原样留到下一次五秒决策；在合法即时操作存在时，紧急命令阶段完成修复，再推进下一轮守将选择。

不能把外部事实伪装成可控保证：开局非法配置、已经发生的城池降级、已锁定的交战及完全无合法解法的状态，都可能使约束暂时不可满足。此时进入显式的 `unsalvageableDefense`，执行最小损失方案，记录阻塞原因；不改等级、不强行挪动锁定英雄、不偷偷删除角色来“通过断言”。

修复过程必须有操作次数上限，不能依靠逐帧循环解雇直到看起来安全。复合操作在同一合法命令阶段执行，不让另一轮进攻插进“解雇筹钱 → 升级”的中间；任何动作失败立即停止依赖它的后续命令并重评估。

### 3.3 防御候选方案及优先次序

**A. 有可用资金且升级能解决险情：优先升级。**

用本城当前合法主持者中内政最高者报价，按每级实际折扣逐级计算；优先升到能容纳计划驻军的最低有效等级。应急可取消尚未执行的远征采购，动用普通战略储蓄；不能误花关键回援的路费。最高五级，超过五人的问题不能只靠升级。已经开战的本场不能因真实等级上涨而虚增 `B`。

“有钱”指完整救城方案可支付，不是账面刚够升级费；若升级后还是必败且会掏空撤离资金，转入其他方案，不能把升级当作无条件消费。

**B. 高级或关键将领能守住：清出低价值挡位将领。**

同时比较调往友城、出城承担有价值任务、解雇筹钱、解雇后升级等方案。资金不足、转移来不及时，解雇会挡住关键将领出场的低价值英雄是合法选项；不是逢普通将领必卖。

每次解雇前算真实返款、当前主持升级的内政价值、兵员容量裁剪、失去的输出和未来被敌国招回的可能成本。主角、正在交战或规则禁止解雇的英雄不能列入候选。尚未解雇的报价不能提前花。

**C. 关键守将单独打不过，但先消耗后能守住：出城野战截击。**

优先让本来会被城池名额浪费、且具备实际交换价值的将领携带合适武器拦截来敌。不能只判断“弱将会不会死”，要比较完整链条：

```text
弱将出击与自动领兵 → 行军粮草 → 实际野战接触
→ 按规则估算可兑现的武器伤害及敌方威胁削减区间
→ 我方确定的出征扣兵与剩余储备 → 关键将领的静态防御余量
→ 城池与关联在外英雄是否保住
```

只有能显著提升保城、保将或争取有效救援时间的牺牲才允许执行。无论牺牲几人都改变不了后果，不应继续送将。必须保留关键守军的真实兵员；当前出征接口自动领最多四兵，AI 不能在预测里假定“弱将零兵出城”，执行却把全国库存领光。需要自选带兵数量时，另立双方通用玩法/API 变更，不默认包含在本计划中。

武器选择以整套计划的边际收益为准，比较小成本有效伤害与昂贵过量伤害；有自伤的武器只在已经计入自伤、能保留出手机会且方案确有收益时使用。城内守方不使用武器。正在与另一英雄交战的敌人不能被同时围攻；其他部队应预测其结束位置或拦截后续敌军。

**D. 城内不利、野外有利：由核心将领主动出城迎敌。**

去掉敌方可利用的守将名额问题，在武器和地形合适时主动野战。必须同时评估空城被另一支敌军占领的后果；出城核心仍归属于原城，绕过截击的敌军占城可能导致核心直接清除。不能只看这场野战的属性优势。

**E. 本城不可守：有时限地撤往友城。**

优先转移核心英雄，选择能在失城前到达、入城后不制造危险溢员、近期也能存续的友城。“大本营”是 AI 选定的安全整备中心，不是当前代码中已有的特殊建筑机制。应按安全、等级、收入、距离、容纳计划选址，不机械回地图第一城。

必须满足：

```text
完成合法调出 + 行军 + 可能拦截 + 进驻时间 + 安全余量
    < 保守预测的原属城失守时刻
```

只跨出城门、正在逃跑、已经到别国城下排队，都不算转移完成。已经触发失城清除标记者不能救活。撤离失败时不谎报“保住高级将领”。

**F. 无安全友城：建立新据点或最后一搏。**

可以转攻弱国，但须在原属城失守前完成夺城并改变英雄归属城，且真实考虑敌城守军、攻城时间、装备、粮草和第三国拦截。所有候选均来不及时，选择存续概率最高的守城、截击或反攻，不无限等待、不派出无资金远征。

若是最后一城，不能以“放弃领土保将”为由自动清空；在当前规则下，无据点英雄往往也不能独立存活。

## 4. 认识敌人：威胁、时间与后果

### 4.1 建立公平的信息视图

自己的金币、库存、英雄和任务全部可知。敌方只使用游戏向玩家公开的城池资料、部队资料、位置、移动方向和可观察战斗状态；现有界面允许查看的敌方国库或守军可纳入。

不能直接读隐藏的敌军最终目的地、AI 内部计划、真实未来随机种子、尚未发生的收成或招募结果。当前威胁判断会读取 `march.target/destination`；新系统要改为基于可见轨迹、距离和合理目标集合的预测。公开信息范围由 `AiObservation` 契约明确定义；未来添加迷雾时只更换观察层。

属性评估是确定性纯函数，不使用随机采样，不消耗或推算真实战役随机序列。只有同分候选的个性偏好可使用独立且可重现的 AI 随机源，不能用它抽样战斗。已知规则与当前属性是判断依据，不是获知下一次随机结果。

### 4.2 每座城的威胁记录

记录敌人接触城堡的预计时间区间、可能的野战接触、入侵可信度、敌军组合、先后次序、最早危险窗口、当前守军风险等级，以及城池失守会清除的在外英雄价值。

威胁分为观察、预警、紧急、交战、不可守。不同等级用行动时限和损失规模界定，而不只用一个固定距离：山地很近也可能来得慢，平地更远的强将可能先到。

对多支来敌，按真实接触规则识别排队顺序、可能上场的守将及后续威胁；用有界的最强对局、预计损耗区间和储备压力评估整条防线，不逐轮制造假想战果。守方获胜恢复与兵员归还、城防可能损伤、后续重新开场均是评估约束。不能把所有敌军战力简单相加，更不能只检查最先来的弱将；跨越多轮时降低评估可信度，而不是假装知道每轮剩余血量。

“失守时间”是启发式区间，不是通过战斗模拟获得的分布或已知事实。行军时间按合法路线积分；交战耗时按公开阶段时长、当前可见进度和保守经验范围估计，不预演碰撞。无法给出可靠交战下界时，以最早接触等更早危险窗口规划，不凭空借用战斗拖延时间。未知敌方计划或长链条判断需要增加安全余量。

### 4.3 全部城市参与优先级比较

不再把“最多处理两城”当作忽略其他危险城的规则。全部城市保留威胁记录与截止时间；计算可错峰，紧急命令不能因为排名第三而永远漏掉。

城市价值包含当前收入、下一月可实现收入、本土/外国折算、升级价值、附近交通时间、关键驻军和所有仍依赖该城的外出英雄。最后一城和关键关联城具有更高的存续权重。

小股佯攻只牵制必要力量，不能让整个国家永久停攻；外攻只有在会抢走必要救援资源或使本国存续风险越界时才暂停。

## 5. 静态攻防评估：只看属性、装备与规则，不模拟战斗

### 5.1 输入与输出

输入使用可观察的双方当前 HP、实际随行士兵及生命、战斗属性、士气状态、携带武器及顺序、武器当前是否可用、城防开场等级/剩余名额、地形、双方合法行动与全国实际可调拨资源。高级类型仅参与英雄战略价值，不直接等于对局胜利。

输出 `CombatAssessment`：优势/接近/劣势/信息不足、攻防余量区间、武器威胁、关键将领风险、行动时限范围、判断依据及保守性标签。不输出未经实战验证的“73% 胜率”或虚假的统计置信区间。

同一份观察与配置应得到同一评估。属性评分、候选计划比较与真实行动执行明确分开；评估器不导入战役或战斗引擎。

### 5.2 静态对局指标

先按公开规则计算有效攻击修正，城防、地形、士兵和士气分开处理；不能把城防加成算进士气、把将领地形惩罚算到不受该规则影响的士兵上。共享纯规则函数与配置，不共享战斗执行器。

可以使用以下作为第一版相对优势指标，而非完整战斗公式：

```text
H = 当前将领 HP + 当前实际小兵 HP 之和
H_我* = max(0, H_我 − 来敌可兑现武器伤害 − 我方武器自伤)
H_敌* = max(0, H_敌 − 我方可兑现武器伤害 − 敌方相应自伤)
M = H_我* × D_我 − H_敌* × D_敌
```

`D` 是由有效属性、兵员和可见士气得到的静态伤害效率估计，双方使用相同单位。`M` 衡量承伤能力与输出的相对关系，不是命中次数或胜率。它不更新任何假想生命、兵员、士气，也不循环到胜负；兵员减少后的输出变化、首轮爆发、近战时机等未充分建模因素通过明确风险修正体现，不能宣称该式等价于真实战斗。

对我方输出与武器兑现取较保守值、敌方取较不利值，形成保守余量；反向参数形成有利余量。整个区间明显有利时才标记优势；区间跨越零或信息不足时标记不确定。安全阈值是待校准的配置，不当成统计概率。若双方可能被武器瞬间击败，单独标记释放顺序风险，不能因公式同为零而宣布平局。

### 5.3 武器必须按可兑现价值计算

只计实际携带或能在合法出发前购入并装载的武器，不把国家仓库当作野外英雄背包。守城方的武器攻击贡献为零，野战和攻城进攻方按现行允许条件计算。

至多三件武器可以逐件做静态效果与用途分类，但不预演“使用后碰撞、再使用、再死亡”的战斗序列。开场已由规则确保可释放的武器，仍要核验存活与合法阶段；后续依赖碰撞、概率或出手机会的武器，不能把总伤害全部记成必达。防御保守项可高估敌方威胁，但为主动牺牲部队计算的收益必须有可说明的兑现依据，没有依据时下限按零处理。

纳入攻击先扣兵后伤将、自伤、过量伤害、首件武器顺序、武器解锁、价格、库存与使用限制。当前工作区的自动释放规则由真实引擎执行，AI 不能代替引擎掷骰或抢先释放。武器顺序只有在玩家同样可调整的范围内才是决策变量。

### 5.4 守城与消耗方案如何比较

先筛真正可能上场的守将，按 `initialCityLevel − victories` 排除无上场资格的后排战力。再对关键守将与主要来敌做静态对局评估，同时保留剩余敌军、兵员储备、城防损伤与失城关联英雄的风险。不能把多个英雄的 HP 简单合成一支不会被逐个击败的大军。

候选方案包括：最小有效升级；保留高内政主持者后升级；解雇挡位筹款；调防；武器截击；全国回援；提前撤往友城；建立新据点。即时升级、解雇、扣钱与自动领兵是确定规则，可以在资源账本中逐项核算。含未来战斗的部分只重新计算静态指标和风险，不递归产生假想战后状态。

消耗方案须证明“按可说明的伤害下限或保守区间，关键守将的对局风险有实质改善”，同时核算带走的士兵、装备价格和粮草；不能因为纸面能扔三件武器就派弱将送死。没有可靠伤害下限时，可以比较有风险的最后一搏，但不能称为已证实能保城。

只在合法、及时、资源可支付且不制造危险溢员的候选中选最优评分方案。未知敌方改令、战斗随机性和启发式误差使它不是全局最优或必胜保证；真人式判断允许失误，但应能解释并避免重复明显错误。

### 5.5 校验与成本边界

核验纯规则映射的边界、装备兑现条件与局部单调性；用人工构造的规则场景及实际发生的完整对局记录校准风险阈值。允许回归测试运行真实游戏验证新 AI，但不能为一次决策额外试打，也不以批量模拟生成运行时胜率表。

每次仅比较有限宏观方案与候选英雄；明确上限并按请求记录静态评估调用数。缓存键包含有效属性、装备与规则版本、场地和兵员分配；普通坐标移动不让无关对局评估失效。缓存结果执行前仍需校验。

预算耗尽返回已完成的最佳合法方案及 `budgetLimited`，不存在样本数、模拟步数或后台试打任务。参数和耗时目标均需要目标设备验证。

## 6. 全国资源管理：现金流与任务预留

### 6.1 一套国家账本

国家账本分为：真实现存资源、已承诺的关键任务预留、可取消的远征/建设预留、剩余可支配资源。预留不是把金币从游戏中扣走，而是限制其他 AI 计划重复使用。

账本覆盖金币、当前全国兵员、具体武器类型和数量、英雄占用，以及各危险城在预计入城时刻的安全名额。对实际自动领兵行为必须按命令顺序精确执行，不能用预留假设覆盖真实扣兵顺序。

每次动作成功后立即用新状态重算；任务取消、失效、阵亡、进驻和战斗结束释放对应预留。一个英雄只能接受一个当前任务，同一支援军不能同时被两城计算在内。

### 6.2 看最低现金点，而不是只看月收入

对候选方案及合理的不利场景，沿时间线计算：

```text
余额(t) = 当前金币
        + 已实际发生的解雇收入
        + 截至 t 已结算、仍保有城池的收入
        - 已执行的升级、征兵、招募和武器费
        - 截至 t 产生的粮草与月俸
```

分别检查月结前、月结后、援军到家前和攻城排队期间的现金低点。不能预花下月收入，不能把“准备占下”的外国城当成已到账收益，不能把余额被规则截成零当作没有违约/断粮后果。

粮草按每名英雄已有零头、行军/扎营/交战时间和实际到家时刻计算；调令和改路不清零。预测城池可能失守后，要移除对应后续收入。已有在外部队和拟派部队合并核算。

### 6.3 应急不等于死守固定余额

普通阶段保留经营和远征缓冲。紧急阶段可以动用通常的五金币缓冲，取消未执行的远征装备预留，并召回不能继续供养的远征；但必须保留当前救援计划所需现金，移动中不能因升级而到零停步。

最后一城即将失守时，允许花光不再有战略意义的储蓄实施可行救城；同时承认完全零金币会限制哪些行动。不要在灭国前坚持“预算要求留五金币，所以什么都不做”。

### 6.4 支出必须服务于任务

升级分别评估保命、容纳守军、招募空间、收入和兵员容量；有主持者时按真实内政报价。征兵按最近战斗和出击的边际需求补，不无脑灌满全国上限。武器只为明确可执行任务购买，现有库存也有机会成本。招募必须有容纳位置、未来任务和可承受月俸。

普通英雄也可以是优秀的内政主持者、低成本守军或有效截击者；高级英雄也可能残血、无兵且当前对局不利。英雄价值由不可替代性、对局能力、内政节省、战略角色、培养/替代成本和月俸共同决定。

## 7. 全国调度与回援：已经出征的英雄仍归国家控制

### 7.1 持续任务模型

每名英雄维护任务：驻守、整备、调防、野外截击、救援、远征、攻城排队、撤离或战斗撤退返程。任务记录目的、目标城市/敌军、起点、当前阶段、截止时间、资金与装备承诺、关联行动、失败条件及后续计划。

例如不是只记录“去城市 A”，而是“在 A 的保守失守时刻前到达外侧截击点，避免入城溢员；威胁解除后补给，再根据局势决定是否恢复远征”。

### 7.2 来得及才算援军

对每名候选计算从当前位置出发的真实行军时间、地形、合法分段路径、沿途敌城、可能野战、断粮风险，以及其离开旧任务造成的机会损失。

```text
有效回援 = 能合法接新命令
        且 救援/截击可在危险截止时间前发生
        且 完整预算可支付
        且 不制造更大的失城连锁损失
        且 到达后的战力确实有用
```

默认优先召回可自由改道、能及时抵达、救援增益大的部队，而不是无条件所有人回城。若一名就足够，不召回三名；多城受袭要联合分配英雄，不能各城市独立选择同一名高级将领。

### 7.3 分清部队状态

| 当前状态 | 可做的事 | 不允许的事 |
|---|---|---|
| 行军、普通扎营、未开战的城下排队 | 通过统一命令接口改道回援、转城或截击 | 忽略粮草、瞬移、保留不再有效的攻城排队位置 |
| 正在野战或作为攻方交战 | 比较继续打完与合法战斗撤退；先记录战后任务 | 免费脱战、当帧改道回家 |
| 正在守城 | 继续守城；其他部队配合救援 | 主动战斗撤退、解雇、强行调出 |
| 已进入战斗撤退返程 | 按既有原路和锁定规则继续；监控出发城是否安全 | 任意改成另一条进攻路线 |
| 出发城失守且已有清除标记 | 不再承诺其未来战力，按规则收尾 | 借重新夺城撤销标记 |

对战斗锁定者，`回援时间 = 剩余交战/撤退时间 + 返程时间`，不是地图直线距离。撤退只有 40% 基础成功率，因此“为了回援把本来能赢的高级将领送进六成死亡判定”通常不是好方案；必须比较整体存续收益。

### 7.4 回援不必进城

可执行城外截击、拦下一支来敌、提前入城换防、护送核心转移、延迟敌军直到守将完成升级等任务。入城会导致 `H > B` 时，应先安排合法调出或升级，或改在野外发挥作用；禁止把英雄当成额外城墙堆在一级城。

友军不能替换正在交战的守将，也不能多人同时攻击一个已锁定的敌军。对正在攻城的敌军，援军可处理其他来敌或等待其可接触阶段，不能凭空中断城战。

威胁解除后重评估原目标、敌情和预算，不能盲目沿用旧远征。为普通改令设置承诺期和收益差阈值，防止同一英雄每次决策在回家/进攻之间来回折返；紧急危险、目标易主、断粮可打断承诺期。

## 8. 从守国到统一：国家长期战略

国家阶段是方向，不是互斥按钮：整备、扩张、主动防御、战略收缩、优势推进、终局围攻。在不抢占救国资源时，可以一边防御局部威胁一边执行高收益远征。

### 8.1 目标选择

对每个可达目标比较：属性与装备层面的可攻性、占领后守住的风险、本土/外国实际收益、消灭敌方关联部队的收益、缩短己方战线、对最大对手的影响、行军与排队成本、将领损失风险、武器成本，以及从出发城抽走部队造成的风险。

弱国是优先机会，不是永远无条件进攻最弱国。若最大的对手正在形成不可逆优势，允许在预算和胜算成立时压制其要害。仇恨只作有限的偏好修正，不能让 AI 为报复撞强城、忽视老家或拒绝更好的统一路径。

### 8.2 先组成可完成任务的队伍

一次远征明确参战英雄、顺序、装备、兵员、到达窗口、队列时长、失败处理及回援阈值。各部队可以分散进攻不同弱点，但同一目标的投入不应无上限增加；额外部队只有能提高任务成功或减少重大损失时才加入。

准备阶段发现目标升级、增援或我方老家受袭，允许取消并释放预留。行动后已经产生的费用是沉没成本，不能成为继续送死的理由。

### 8.3 攻击来敌的归属城

这是可用的间接救援方案：若能在关键截止时间前占领来敌的归属城，可能清除尚未交战的该城部队。但对已经交战者，只会产生战后清除，不会当场中断其对我方的伤害。预测必须按实际顺序结算，不能把“偷家成功”直接当成“本城必定得救”。

### 8.4 占领后整备

占领会重置城池为一级，兵员上限和归属改变，不赠送敌方库存。入城完成后立刻重新建立安全驻军和关联城关系，安排升级、调防、回补和下一阶段任务。不得将连续到达的全部高级将领囤在新占领的一级城。

### 8.5 终局与防止停滞

不把“金币最多”当胜利；最终目标是拥有当前世界全部城池。最后的强国需要集中兵力、武器与经济优势，不继续无限招募和储蓄。

若若干战略周期无进展，必须给出原因：无可胜目标、资金短缺、补给距离、核心城风险、属性评估不确定或计划反复失效。先修复真实瓶颈，再在国家有充足余力时逐步放宽一般进攻风险；不能把无限保守当稳定，也不能用定时无脑自杀打破僵局。

当前 `CampaignState` 会在玩家失败时冻结世界，因此单局界面可能在 NPC 完成全部统一前结束。正式游戏是否展示“某国统一”的独立胜利结算是另一个明确需求；离线 AI 对战应使用可配置的全局终局策略测试入口，不能临时删除玩家失败规则来跑成绩。

## 9. 决策算法：比较整套计划，不堆更多 if

### 9.1 总流程

```text
读取公平观察与当前任务
→ 更新全城威胁、截止时间、失城关联损失
→ 检查硬约束，生成紧急修复候选
→ 生成升级/调防/解雇/截击/回援/撤离等组合计划
→ 在只读规划账本中核算确定的即时动作和资源扣减
→ 排除不可行和明显劣势方案
→ 依据属性、装备、规则与风险余量比较候选，不预演战斗
→ 联合分配全国英雄、现金、兵员、武器和入城名额
→ 选择风险可接受且长期收益最好的计划
→ 版本校验后提交合法命令
→ 根据战况与执行反馈继续或重规划
```

### 9.2 先约束，后评分

非法动作、重复承诺、可避免的危险溢员、无法支付的关键现金流和明显超出时限的救援先剔除，不能靠“占城得分高”抵消。

剩余方案按国家存续、核心战力和长期统一收益比较。可使用词典序优先级，再在风险容许范围内比较归一化收益：

```text
收益 = 可持续领土增长 + 敌方关键能力损失 + 我方未来战力
     + 确实到账的经济增益
     - 我方将领损失 - 装备与粮草消耗 - 暴露的失城风险
     - 新增任务对既有关键计划的机会成本
```

这些权重是调参项，不是已经证明有效的常数。紧急防御更重视保守存续条件；一般扩张容许有限风险；核心保全同时检查不利条件下的损失，评分不是抽样战果的均值或分位数。

### 9.3 受限组合搜索

使用宏观动作模板加受限宽度搜索：例如“先保留高内政主持者升级，再调出低价值英雄”，或“解雇一人筹资，给另一人带武器截击，召回最近高级将领”。不是穷举所有英雄、装备和所有未来帧。

先用有限动作模板产生少量非劣方案；若方案甲花费不高于乙、存续风险不高于乙、保留战力不低于乙且时限也不差，可剔除乙。第一版可将最终完整方案上限设为 8，组合深度以 2–3 个资源/调度动作起步；另给候选展开总数、英雄候选和路线积分设置硬上限，不能只限制最终输出数量。该数字仅为待压测起点，不搜索未来战斗回合。

多城救援使用小规模联合任务分配或受限搜索，计算每增加一名英雄带来的边际救援收益与另一任务的损失，而不是只按英雄强弱贪心。相近方案允许稳定的小随机偏好，不能随机选择明显被支配的坏方案。

搜索没有完成时，执行已知安全的保底方案。绝不声称这种有预算的规划器能算出所有情况下的全局最优。

## 10. 执行架构与性能：原生 Isolate，Web Worker

### 10.1 默认将国家规划移出 UI 主执行环境

采用一个常驻 `AiWorker` 服务全部国家，而非十个国家创建十个工作线程。各国保留独立任务、资源账本与信息视图；共享计算服务不等于共享情报或互相协作。

| 平台 | 正式执行后端 | 注意事项 |
|---|---|---|
| Android / iOS / Windows / macOS / Linux | 一个由 `Isolate.spawn` 启动的常驻 Isolate，Ports 通信 | 不在每次决策重复 `Isolate.run`/`compute` 创建销毁；不共享可变战役对象 |
| Flutter Web | 一个常驻 Dedicated Web Worker，消息通信 | Dart Web 不支持原生 Isolate；`compute()` 在 Web 当前事件循环执行，不是并行后端 |
| 测试/显式降级 | 同一纯 Dart 规划器的确定性驱动或严格分片执行 | 不能静默把完整重决策退回主线程；降级状态和成本必须可见 |

以上平台事实依据官方资料 [W1–W5]；这里是实施设计，尚未完成 Worker 或 Isolate 集成与实机验证。

```text
主执行环境：真实世界更新、输入、绘制、有限安全检查
    └─ 发送一致的纯数据观察和任务请求
AiWorker：属性评估、预算、目标选择、救援调度、有限方案比较
    └─ 返回带前置条件和有效期的行动建议
主执行环境：在固定命令阶段校验并执行合法指令
```

真实 `CampaignState` 只有一个写入者。工作环境不推进真实世界、不调用战斗引擎、不操作 Widget/Painter/图片或通过 `rootBundle` 读取资源。主循环正常继续，不能等 AI 结果才允许下一帧；异步回复进入结果队列，在规则安全的阶段提交。

### 10.2 共享算法与跨平台消息

将策略核心提取为纯 Dart 模块，禁止直接或间接导入 Flutter、`dart:ui`、`campaign.dart`、`battle_simulation.dart` 和 `nes_battle_kernel.dart`；位置使用普通数值坐标。消息格式限定为编号、数字、布尔值、枚举编码、数组和显式序列化的数据记录，Web 端转换为可结构化克隆的 JS 数据或类型化字节数组，不直接 `postMessage` 任意 Dart 实例。

主环境装载规则、武器目录、地形速度与城池轮廓等静态数据，在初始化时发送一次；资源或玩法变更使用 `rulesVersion/mapVersion` 重建或更新。每次决策只发相关国家和可观察威胁的紧凑快照；不每帧复制完整世界，不传贴图、战斗 RAM、完整英雄对象图。动态增量如采用镜像需携带基线版本，丢失增量后重同步；第一版优先使用有界小快照减少协议复杂度。

Web 需增加独立 worker 入口及单独编译/部署步骤，第一版可将同一纯 Dart 核心编译为 JS worker，使用 JS interop 与浏览器消息接口接入。Flutter Web UI 采用 JS 还是 Wasm 不改变该通信分层，也不会自动得到 Dart Isolate 支持。必须验证 worker 文件地址、站点子路径、MIME、CSP、版本缓存及启动握手；不能把 Flutter 构建默认会包含该入口当作前提。普通消息方案不依赖共享内存。

开发与发布都必须生成匹配的 worker 产物；热重载后若 UI 与 worker 规则或协议不同，要明确重新构建/重启，不能沿用旧策略代码而显示集成成功。

### 10.3 过期、幂等与国家间公平

请求携带 `sessionId`、`countryId`、`requestId`、`observedTick`、`rulesVersion`、相关实体/任务版本和逻辑截止时间。结果附带行动前置条件、资源预留、原因与 `budgetLimited`。

执行前复核：仍在同一局与规则版本；英雄仍属于该国、存活且未锁定；城市归属、可用金币/兵员/武器和安全名额仍满足；回援从当前位置仍来得及。失败则丢弃该动作及依赖动作、释放预留并请求局部重算，不能为了用上结果而强制执行。

不要把每次世界 tick 都增加的全局版本当作全部结果的失效条件，否则不断移动的世界会让结果永久过期；使用依赖实体版本、关键条件和时效窗口。位置轻微变化可重算到达校验，不能忽略重大改令或敌情变化。

每国至多保留一个最新待办请求，全局一个执行中请求；紧急事件合并到该国最新请求并提高优先级。规划过程必须在有限步骤后检查取消并让出工作环境事件循环，保证新威胁、重启和停止消息能被处理。排序结合危险截止时间和等待时长，防止和平国家长期饿死。队列不随 60Hz 更新无限增长。

结果及命令具有去重编号；一次复合计划中的英雄解雇、采购和调兵不得因重复消息执行两次。多国共享招募池等真实资源的变化，仍以主环境统一合法命令的实际结果为准。

### 10.4 主环境只留轻量安全保护

主环境保留确定性、受限的守城安全校验和命令执行，不保留完整战略规划副本。已验证的应急预案可以在相关规则事件前复核后执行；无有效预案时阻止新危险操作、发起最高优先级请求，并执行确实存在的少量合法保底动作。不能为了等 worker 暂停敌军、冻结战斗或无条件解雇英雄。

当前 `advance()` 内抵达/开战早于常规决策；应增设明确命令提交点，已知安全动作在接触和下一轮守将选择前处理，新的事实在结算一致后通知 AI，不在结算中重入规划。提前按危险窗口发请求，不能指望跨线程回复总能在同一逻辑步到达。开局建立预案，无法及时或合法修复的状态如实标记。

每国常规战略仍可按 3–5 秒错峰和关键事件触发；属性、装备、归属、资金变化更新相关决策，位置更新只影响必要路线与时限。真实战斗的自动武器触发仍由引擎处理，不让 AI 另跑战斗时间线。

### 10.5 限制总工作量，而非只换线程

全部国家共享有界候选、路线积分、命令与消息配额。工作环境也不能一直满载：限制单请求展开次数、任务持续时间和每周期总运算，超过预算返回已完成方案或先执行预案，减少候选而非追加战斗试算。时间限制必须有短步骤检查，不能等一个长同步任务结束后才判断超时。

主线程打包、发送、接收、校验与命令执行也计入 UI 成本，可将每显示帧合计约 0.5–1ms 作为初始待实测目标，并单独约束最大不可中断片段。该目标不是硬实时保证；`SendPort` 复制、Web 编码/克隆、分配回收都须测量 [W1,W2]。降低调用频率、复用静态数据优先于复杂零拷贝优化。

补跑固定逻辑步不能重复补做已过时的十轮战略决策，合并为最新请求；真实世界推进规则不因此偷偷改变。设备暂停/恢复、地图切换或新局开始使旧请求失效。worker 启动失败/崩溃/失联要有有界重启和显式降级，不能无限重试或在 UI 线程一次性接手整个任务。

测试固定观察、操作配额和命令提交序列时应可重现结果；真实跨线程调度延迟可能改变实际落地时刻，不能宣称同种子在不同设备自动产生完全相同整局。需要整局重放时记录命令与提交逻辑 tick。

### 10.6 验证要求

同时记录快照字节数和准备耗时、通信耗时、纯规划耗时、队列等待、观察年龄、过期率、有效回援延迟、主线程最长片段、帧分位数及长期内存/负载。分别在 Debug 的复杂页面与目标设备 profile/release 验证；无渲染逻辑测试不代替实际画面。

必须覆盖十国同一时间受袭、月结/占城/战斗收尾重叠、恶意频繁改令、重复/迟到消息、worker 冷启动和恢复。Web 验证真实 worker 中执行而非 `compute` 主线程兜底，同时覆盖项目采用的 JS/Wasm 构建路径；确认候选截止前能落地，而不是只证明 UI 没掉帧。

## 11. 推荐模块边界

不要继续把全部策略写成能随意访问 `CampaignState` 私有成员的巨大 extension。保留真实战役状态与结算，在其外建立纯数据的规划层。

建议目录为 `lib/world/ai/`，按职责逐步建立以下模块；文件可在规模较小时合并，不为拆文件而拆文件。

| 模块 | 职责 |
|---|---|
| `observation.dart` | 公平观察、不可变国家/城市/英雄/战斗快照，明确可见性 |
| `rules_adapter.dart` | 查询合法动作、真实升级报价、兵员/招募/移动/撤退约束；不决策 |
| `threats.dart` | 敌军轨迹推断、接触时间、攻城序列、失城关联损失 |
| `combat_assessment.dart` | 纯属性/装备静态优势、风险区间与原因；不依赖战斗执行器 |
| `budget.dart` | 全国现金流、兵员/武器/英雄/入城名额预留 |
| `defense_planner.dart` | 危险溢员修复、升级、解雇、消耗、换防与弃城候选 |
| `operations.dart` | 持续任务、全国回援、远征及撤离编排 |
| `country_brain.dart` | 阶段目标、受限组合搜索、全国计划选择 |
| `executor.dart` | 版本检查、合法命令执行、成功反馈与预留释放 |
| `diagnostics.dart` | 可解释决策、指标、测试记录 |
| `runtime/` | 统一 `AiWorker` 协议、原生常驻 Isolate、Web Worker 及显式测试/分片后端 |
| `rules_data.dart` | 可序列化的共享纯规则数据与版本，避免与真实引擎分叉 |

关键数据应包含：

```text
AiObservation：观察时刻、观察版本、国家视图、可见敌情
CityDefenseReport：H、B、真实守将顺序、危险时间区间、关键英雄风险
ArmyTask：英雄、角色、目标、阶段、截止时间、任务依赖、承诺期
ResourceReservation：金币时序、兵员、武器、英雄、计划入城名额
CountryPlan：前置条件、即时动作、持续任务、风险、预留、退出条件
CombatAssessment：优势类别、余量区间、武器威胁、时限范围、判断依据
AiRequest/AiReply：会话/请求/规则/实体版本、截止时间、建议、预算截断原因
CommandResult：成功/失败、实际消耗、状态版本、失败原因
```

当前 `CampaignState.moveTo` 与 `camp` 仅接受玩家英雄。需要扩展为具有 `countryId` 权限参数的统一合法命令入口，默认仍为玩家，保留全部战斗锁定、失城标记、零金币和归属校验。AI 不能继续绕过这些检查直接改写 `HeroMarch`。同一时刻只允许一套 AI 执行器接管，旧扩张与新防御不能各自独立发命令抢英雄。

第一版不要求把整个战役改成不可变状态或完全重写事件系统；可用小范围状态版本、事务式即时动作组和规则适配器建立边界。规则适配分两端：主环境调用真实合法命令与报价，工作环境只读纯规则与快照；不能把闭包或 `CampaignState` 传到工作环境冒充共享状态。

## 12. 可解释性与难度

每次有意义的计划记录：为什么判断危险、城池安全名额、实际敌人及到达估计、候选方案、为什么淘汰、关键预测、资源账本、召回名单和执行结果。日志要有界，不逐帧灌满。

示例日志格式（仅为格式示例，不是真实运行结果）：

```text
A 城进入紧急防御：等级 1，驻军 3，本场未开始，可用名额 1。
升级方案：资金不能同时覆盖回援粮草，取消普通远征采购后仍不足。
换防方案：最近安全友城到达时间超过原城危险窗口。
执行方案：解雇挡位且交换价值低的普通将领；召回 H7 至城外截击。
入城限制：H7 暂不入城，避免再次溢员；状态变化后重新评估。
```

难度优先调反应延迟、候选数量、评估安全余量和风险偏好，不调免费资金或隐藏情报。各国可以有稳健、扩张、灵活等偏好，但共享相同合法性与安全底线。敌国 AI 彼此独立竞争统一，不能暗中共享国库、私有信息或专门联盟只针对玩家。

## 13. 实施顺序与交付门槛

### 前置交付：纯 Dart 边界与工作后端

先定义观察/建议协议及规则数据，验证原生常驻 Isolate 和 Web Worker 的往返、版本检查、关闭重启和超时处理；建立禁止依赖战斗内核与 Flutter 的边界测试。P0/P1 的正式国家规划通过该后端执行，主环境仅有界校验与保底；不能先承诺跨平台后台执行，再只交付主线程版本。

### P0：先修会白送高级将领的防御漏洞

引入 `H/B` 和真实守将序列评估；威胁下停止危险招募；把留守配置降为可被安全约束覆盖的偏好；支持有效升级、合法解雇/调出、最低现金约束；加入命令时序保护和基础诊断。

交付门槛：固定反例中不再出现“有合法修复方案却让低级守将耗尽城池名额、后排高级将领未上场就被清除”；战中升级不被误认为增加本场名额。此阶段只能称防御安全修复，不宣称完整战略 AI 已完成。

### P1：资源账本、统一命令与全国回援

统一 AI 和玩家行动合法性；增加任务状态与预留；从真实位置调回在外部队；比较救援时限，处理多城竞争、入城名额和战斗锁定。

交付门槛：老家受袭能召回必要且来得及的英雄；不重复承诺、不免费脱战、不因回援制造新的溢员；无法救城时能给出原因。

### P2：静态攻防评估与战术组合

实现纯属性/装备评估、真实守将资格、兵员与资源约束；加入有依据的武器截击、核心野外迎战、时限撤离与再建据点。移除旧 `_projectRaid` 的逐轮伤亡推演依赖，不能把它当成无模拟评估器继续使用。

交付门槛：评估不创建任何假想战斗、不修改真实状态或随机流；不把风险分数当胜率；消耗方案按可兑现收益和兵员代价比较，在规则场景及真实对局验证中表现可解释。

### P3：长期统一与经济经营

按可持续领土收益规划目标，控制仇恨权重，集中处理强国，建立占领后整备与停滞诊断；将旧进攻逻辑逐步接入统一执行器并移除重复入口。

交付门槛：能完成完整的扩张—遭袭—回援—整备—再扩张流程，不长期有钱有人却无可解释地停摆。

### P4：多种子对抗、性能与回归

允许在独立回归验证中实际运行游戏，对旧 AI、固定脚本对手和新 AI 自对弈，轮换地图、国家位置与经济条件；报告实际对局数、损失及不确定性，不把这些验证改成运行时隐藏的战斗采样服务。新增计划只跑相关测试子集，完整长局与全量测试在明确安排后执行，不能拿历史构建日志当本次验证结果。

交付门槛：安全约束通过，实际策略结果优于基线的证据充分，性能预算可控；仍失败的场景明确记录而不是掩盖。

## 14. 必须覆盖的验收场景

### 14.1 守城与名额

| 编号 | 场景 | 必须观察到的行为 |
|---|---|---|
| D01 | 一级城，多位驻军，有充足可用升级费，尚未开战 | 优先完成有效升级，或有明确更优理由；计划后 `H <= B` |
| D02 | 一级城，普通将挡住能取胜的高级将，没有升级资金 | 比较转移/解雇，合法清出挡位，不让高级将未上场就随城死亡 |
| D03 | 实际零金币，拟让普通将带武器出城 | 先找到真实筹款/可及时结算来源；不能零金币出征 |
| D04 | 高内政普通将可以低价主持救城升级 | 不先机械解雇主持者，完整比较动作顺序 |
| D05 | 五级城仍有六名驻军 | 不尝试第六级，安排调出或解雇等合法修复 |
| D06 | 本场一级城已开战，建筑升到三级 | 本场安全名额仍按开场值计算，不把后排将领视为安全 |
| D07 | 本场三级城已有两次攻方胜轮，剩余多名驻军 | 按剩余一个名额处理，并尊重当前守将锁定 |
| D08 | 默认 `requiredGarrison=2` 的一级城受袭 | 战时安全约束覆盖默认留守偏好 |
| D09 | 威胁下招募或援军即将入城造成溢员 | 招募被规划器禁止；援军改截击、调防或先修复名额 |
| D10 | 城防在战后下降、下一支攻城军已排队 | 在下一场守将选取前处理已知危险，不能等五秒 |
| D11 | 当前守将锁定，尚未出场英雄可以调出 | 只操作合法英雄，不伪造守将出场顺序 |
| D12 | H 已不超 B，但关键守将仍打不过 | 不把数量安全误报为守城必胜 |

### 14.2 消耗、撤离与游戏规则

| 编号 | 场景 | 必须观察到的行为 |
|---|---|---|
| T01 | 普通将携武器野战后能使核心守将获胜 | 可选择完整消耗链，并核算牺牲、装备和粮草 |
| T02 | 普通将自动领兵会耗光高级守军储备 | 重新安排资金/兵员/动作顺序，不能用假想零兵出征 |
| T03 | 无论怎样消耗都不能改善存续 | 不连续送将；比较撤离、据点转移或最后一搏 |
| T04 | 城内守将有国家武器库存 | 不允许守方使用武器或把库存算成直接输出 |
| T05 | 低价武器足够改变战果 | 不无意义使用高价库存；自伤与过量伤害计入比较 |
| T06 | 拦截对象已经和另一英雄交战 | 不多人并打，不复制敌军战斗状态 |
| T07 | 英雄已出城但在到友城前原城失守 | 预测为失败转移，按真实清除规则验收 |
| T08 | 英雄在原城失守前成功进驻友城 | 确认归属城变更，实际保住英雄 |
| T09 | 已标记失城战后清除，再占领其他城 | 不撤销标记，不把此人算成国家未来战力 |
| T10 | 无友城但附近弱城可及时拿下 | 可以筹划再建据点；超过失城期限就剔除该方案 |
| T11 | 偷袭来敌归属城时，敌人已在攻我城 | 不假设敌人立即停战；计算其战后才清除的后果 |
| T12 | 逃生路线穿过敌城、第三国或危险野战区域 | 路线与时间预测反映真实接触，不按穿越无事处理 |

### 14.3 全国回援与资源

| 编号 | 场景 | 必须观察到的行为 |
|---|---|---|
| R01 | 外出高级将领能及时救回老家 | 取消/调整远征并合法回援 |
| R02 | 外出部队太远 | 不虚报救援成功，改评估本地防御与转移 |
| R03 | 两城同时求援，只有一名合适英雄 | 联合比较并单次分配，不重复使用 |
| R04 | 一名英雄足够保城 | 保留不影响安全的其他远征，不全军回头 |
| R05 | 一级城已有一名守将，援军到来 | 不盲目入城，安排截击/换防/有效升级 |
| R06 | 援军正在野战或作为攻方战斗 | 等待合法战后任务或评估风险撤退，不免费脱战 |
| R07 | 援军处于既有撤退返程锁定 | 不任意重定向；计算原路和出发城安全 |
| R08 | 小股敌军反复靠近又远离 | 不全国家永久停攻，命令不反复抖动 |
| R09 | 两城同时消费相同金币、兵员和一件武器 | 统一预留，不超卖、不重复扣减 |
| R10 | 升级会耗掉正在回援部队的最后粮草 | 选择完整可行计划，必要时动用非关键储蓄而非挪救援费 |
| R11 | 月结前有粮草支出，下月有高收入 | 不预花尚未到账收入；欠收场景检查现金低点 |
| R12 | 解雇英雄导致容量下降且兵员被裁掉 | 预测和执行后的储备一致，不重复返款 |
| R13 | 敌城易主、原目标消失或英雄阵亡 | 释放任务和资源预留，过期命令不执行 |
| R14 | 同国局部遭袭但其他远征不影响救援 | 局部防御与有效扩张可并行 |

### 14.4 预测、公平性与整局表现

必须加入以下性质测试：静态评估前后真实生命/装备/库存完全不变；评估次数不改变真实战斗和月结随机序列；核心没有对战斗引擎或逐轮扣血逻辑的依赖；隐藏敌军目的地或随机种子改变但可见观察相同，AI 不得获得先知行为；固定观察、同分偏好种子和操作配额能重现建议；候选比较被预算截断有明确标记。

静态评估应覆盖残血、缺兵、混合武器、自伤、首件及后续武器可兑现性、不同地形、城防开场值、真实守将资格、多人攻城队列和撤退。用独立保留的规则场景及真实对局检验，不借批量试打预生成胜率表，也不用同一组记录既调参又宣布优胜。

整局验证覆盖三张地图、不同国家起点、多种经济条件和种子。指标至少包括：可避免危险溢员次数、关键将领未出场随城清除次数及原因、实际回援成功率、无效回援、断粮停营、资源重复承诺、武器浪费、可行扩张长期不执行、统一/存续表现、AI 计算峰值和命令反复改派频率。

推荐新增测试文件：`country_defense_safety_test.dart`、`country_reinforcement_test.dart`、`country_evacuation_test.dart`、`country_ai_assessment_test.dart`、`country_ai_reservations_test.dart`、`country_ai_information_test.dart`、`country_ai_campaign_test.dart`。原有战斗、失城、兵员、招募、经济与撤退测试必须继续验证玩法没有被 AI 特权绕过。

### 14.5 工作后端与消息正确性

增加原生 isolate 集成、真实浏览器 worker 集成、协议和规则版本不匹配、迟到/重复回复、局部状态改变、入城前被锁定、重开新局、worker 故障和队列公平性验证。相同请求在两种后端上采用稳定排序和数值容差比较建议，不将系统调度差异解释为自动确定性。

必须验证发送返回期间主循环仍推进；Web 不能以 `compute` 的可编译性代替后台执行证明。压力测试包括十国同时请求、事件持续涌入时的取消/合并、普通国家不被饿死、请求容量恒定有界，以及降级时完整重决策不落回主线程。

真实玩法已自动释放武器时，AI 不额外发射同一件、改变释放概率或突破背包顺序；所有决策只能使用当前快照中允许观察的概率参数和已发生结果。

## 15. 最终验收标准

完成后的 AI 应能解释并执行这样的过程：

> 我发现一级城的两名普通将会挡住核心守将。升级报价与回援粮草不能兼顾，于是先取消尚未执行的非必要采购，比较调防和解雇。对手仍然过强时，让真正有交换价值的部队携武器在城外截击，同时召回能赶到的高级将领，但不让援军直接进入已满安全名额的城池。若全部守城方案仍不可行，就在原城失守前把核心进驻安全友城，或完成确实来得及的新据点夺取。危险解除后重新整备并继续扩张，而不是永远停止进攻。

这才算实现了国家级战略控制。只是多加几条“遇敌升级”“血低撤退”“召回所有人”的判断，不算完成本计划。

最终架构要求：国家规划在原生常驻 Isolate / Web 常驻 Worker 执行；主环境只保留真实世界、轻量规则保护和命令提交。AI 只根据属性、装备、规则和资源做有界计划比较，绝不模拟战斗。并行不等于零开销，启发式评估不等于必胜，两点均须在实现与验收中保持明确。

## 16. 跨平台技术依据

以下官方资料于 2026-09-10 核对，平台能力以实施时所用 SDK 与实际构建验证为准：

- [W1] Flutter — Concurrency and isolates：常驻 isolate、消息复制、Web 不支持 isolates、`rootBundle`/UI 限制。`https://docs.flutter.dev/perf/isolates`
- [W2] Dart — Concurrency in Dart：Web Worker 与 isolate 的差别，Worker 需独立入口并单独编译。`https://dart.dev/language/concurrency`
- [W3] Flutter API — compute：Web 在当前事件循环执行，原生在独立 isolate 执行。`https://api.flutter.dev/flutter/foundation/compute.html`
- [W4] Dart — dart compile：纯 Dart 可编译为独立 JavaScript 产物。`https://dart.dev/tools/dart-compile`
- [W5] HTML Standard — Web workers：Dedicated Worker 与消息机制。`https://html.spec.whatwg.org/multipage/workers.html`
- [W6] Dart — JavaScript interoperability：Dart 与 JS 平台接口的通信边界。`https://dart.dev/interop/js-interop`
